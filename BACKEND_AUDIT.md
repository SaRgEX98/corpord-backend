# Аудит backend и план исправлений

Дата: 2026-10-31. Исходники: commit `e762c8b`.
Код приложения не изменялся. P0 — исправить в первую очередь; P1 — существенные
ошибки безопасности или работоспособности; P2 — ошибки контрактов и эксплуатации.

**Что проверено**

- Просмотрены маршруты, middleware, авторизация, SSO, сервисы, репозитории,
  модели, миграции, конфигурация и жизненный цикл приложения.
- `go test ./...` и `go vet ./...` завершились успешно. При этом во всех
  пакетах `[no test files]`: автоматических проверок поведения нет.
- Проверки HTTP и PostgreSQL выполнялись в отдельном временном Compose-проекте
  с образом `ghcr.io/sargex98/corpord-backend:latest`, digest
  `sha256:7847652661911a0cc19857da61e91f4fe34d858e14fbe9a8699f30b625cdb723`.
  Найденные причины проверены по локальным исходникам. Эти интеграционные
  проверки подтверждают поведение образа, а не отдельной сборки из исходников.
- Проверки `state`, callback, CORS и пустого JWT-секрета запускались непосредственно
  на локальном Go-коде через временную программу с `httptest` и подменой Auth-сервиса.
- Тестовые контейнеры, тома и временная программа удалены. Рабочие контейнеры,
  аккаунты и данные не изменялись. Полный вход в реальные Google/Yandex не проверялся.
- Проверка зависимостей на известные уязвимости и нагрузочные тесты не выполнялись.

**Найденные ошибки**

1. **A01 / P0. Обычный пользователь может управлять другими пользователями.**
   В [handler.go](internal/handler/handler.go#L180) GET списка, POST создания
   и DELETE пользователя находятся в общей группе `authorized`, без проверки роли
   и владения записью. В обработчиках дополнительных проверок нет.
   Подтверждено для роли `user`: GET `/api/v1/users` → `200`, POST туда же → `201`,
   DELETE другого тестового пользователя → `204`.
   Исправление: перенести административные операции под `/admin/users`, удалить
   обход через старые маршруты либо защитить их теми же правилами. Для операций
   над собственным профилем использовать ID из проверенных claims.

2. **A02 / P1. OAuth callback не проверяет `state`.**
   [sso.go](internal/handler/sso.go#L46) создаёт state-cookie, но
   [SSOMiddleware](internal/handler/middleware/sso.go#L10) проверяет только провайдера
   и наличие `code`. Ни сравнения `state`, ни его погашения нет.
   Локальная проверка: callback без `state` и cookie доходит до SSOLogin.
   Это убирает защиту от подмены потока входа (login CSRF).
   Исправление: проверять одноразовый state, привязанный к браузерной сессии
   и провайдеру; отклонять отсутствующий, неверный, просроченный и повторный state
   до обращения к token endpoint. Реализовать PKCE вместе с хранением verifier.
   Не записывать state и authorization code в логи.
   Проверка state предусмотрена в [потоке Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect#confirmanti-forgerytoken).

3. **A03 / P1. Ротация refresh создаёт дубликаты, logout не завершает сессию.**
   [auth.Refresh](internal/service/auth.go#L233) вызывает `issueTokens`, который уже
   сохраняет новую refresh-сессию, а затем повторно вставляет тот же хеш через
   [RefreshToken](internal/repository/pg/refresh_token.go#L137), с другим UUID.
   Уникальности `token_hash` в схеме нет. Подтверждено: после одного refresh
   существует две записи с одним хешем; logout возвращает `200`, после чего тот же
   refresh снова принимается и выдаёт новую пару токенов.
   Кроме того, SELECT старой сессии выполняется без блокировки, а UPDATE не проверяет
   `revoked=false`: две конкурентные транзакции могут принять один старый токен.
   Исправление: генерировать токены без побочных записей; проверять/погашать старую
   сессию и вставлять ровно одну новую в одной транзакции. Использовать блокировку
   строки или условный UPDATE с `RETURNING`, проверяя срок действия и число строк.
   Отдельной миграцией очистить дубликаты с безопасным отзывом затронутых сессий
   и добавить уникальный индекс на хеш. Ошибка транзакции не должна оставлять новую
   активную сессию. Повторное использование погашенного токена должно отклоняться.

4. **A04 / P1. `logout/all` не отзывает токены пользователя.**
   [Маршрут](internal/handler/auth.go#L263) зарегистрирован без AuthMiddleware;
   [обработчик](internal/handler/auth.go#L248) читает `user_id`, тогда как middleware
   использует `claims` и `userID`. Фактически вызывается отзыв для ID `0`.
   Подтверждено: без авторизации endpoint возвращает `200`; после вызова с токеном
   реального тестового пользователя его активные сессии сохраняются.
   Исправление: сделать маршрут защищённым, унифицировать получение пользователя
   из claims и проверить отзыв всех его refresh-сессий. Отдельно определить политику
   для уже выпущенных access-токенов: до истечения TTL или немедленно через версию сессии.

5. **A05 / P1. Успешный SSO callback не выполняет HTTP-редирект.**
   [callbackFromProvider](internal/handler/sso.go#L87) сначала пишет JSON с `200`,
   затем вызывает `Redirect(302)`. Заголовок статуса уже отправлен.
   Проверка на исходниках: записан статус `200` и JSON с access token;
   последующий Redirect не заменяет их полноценным ответом `302`.
   Исправление: выбрать один ответ. Для текущего браузерного сценария — установить
   refresh-cookie и вернуть `302` на настроенный frontend callback, без JSON
   и без токенов в URL; frontend получает access через `/auth/refresh`, затем `/users/me`.
   Согласовать это с frontend: его текущий middleware использует `/api/v1/me`
   на своём origin, а backend предоставляет `/api/v1/users/me`.

6. **A06 / P1. Две доступные снаружи ошибки разыменования nil в авторизации.**
   [Register](internal/service/auth.go#L144) разыменовывает `input.Password`, хотя
   в `UserCreate` пароль необязательный указатель. [Login](internal/service/auth.go#L179)
   разыменовывает `PasswordHash`, который штатно равен NULL для SSO-пользователя.
   Оба сценария воспроизведены: запрос заканчивается panic в обработчике и `500`;
   Gin Recovery сохраняет процесс сервера, но корректного ответа API нет.
   Исправление: разделить DTO локальной регистрации и SSO; валидировать обязательный
   пароль до bcrypt; явно обрабатывать отсутствие локального пароля при Login.
   Для неверного ввода возвращать `400`, для невозможного входа — согласованный `401`.

7. **A07 / P1. CORS допускает посторонние домены с префиксом localhost.**
   [CORSMiddleware](internal/handler/middleware/cors.go#L21) использует `HasPrefix`,
   причём независимо от `APP_ENV`. Подтверждено на исходниках:
   `Origin: http://localhost.attacker.example` получает разрешение origin
   и `Access-Control-Allow-Credentials: true`.
   Это подтверждённый обход списка origin; конкретная возможность чтения
   аутентифицированных ответов дополнительно зависит от браузерных cookie-ограничений.
   Исправление: точное сравнение нормализованных scheme/host/port с разрешённым
   списком; локальные исключения только для development; `Vary: Origin`.

8. **A08 / P1. Нет проверки критической конфигурации перед запуском.**
   [config.Load](internal/config/config.go#L150) допускает пустой JWT_SECRET,
   неверные значения bool/int/duration незаметно заменяет дефолтами.
   [token.NewManager](internal/token/manager.go#L45) не отклоняет пустой ключ:
   проверка на исходниках успешно создала и проверила JWT с пустым секретом.
   Это опасно при таком запуске; инфраструктурный Compose требует непустой ключ,
   но сам backend не защищён от запуска с пустым ключом другими способами.
   Google/Yandex регистрируются [безусловно](internal/app/app.go#L79), а поля
   `SSO_*_ENABLED` не учитываются. Поэтому незаполненные настройки провайдера
   превращаются в ссылку с пустым `client_id`, вместо понятной ошибки запуска/отключения.
   Исправление: явная валидация ключа, алгоритма, TTL, портов и обязательных полей
   включённых провайдеров; отключённые провайдеры не регистрировать. Обновить
   backend `.env.example`, Compose и описание включения SSO одновременно.

9. **A09 / P1. Cookie и redirect привязаны к localhost, удаление cookie несогласованно.**
   [SetRefreshCookie](internal/handler/helper/cookie.go#L15) задаёт Domain=localhost,
   callback содержит фиксированный `http://localhost:3000/auth/callback`, а
   logout удаляет cookie с пустым Domain. При другом домене refresh-cookie
   не соответствует адресу API; различающиеся атрибуты могут помешать её удалению.
   Исправление: вынести frontend URL, Domain, Secure и SameSite в проверенную
   конфигурацию. По умолчанию использовать cookie без Domain, если достаточно
   одного API-хоста. Установку и удаление проводить одним helper с совпадающими
   Name/Domain/Path. Проверить HTTP localhost и HTTPS на целевом домене в браузере.

10. **A10 / P1. Два неправильных запроса чтения рейсов.**
    В [trip.All](internal/repository/pg/trip.go#L48) вызывается несуществующий
    `JSON_AGG(name, address, latitude, longitude)`; остановка к тому же зафиксирована
    как `id=1`, вместо привязки к рейсу. Подтверждено: GET `/api/v1/trips/all` → `500`
    с PostgreSQL `42883`, даже на пустой таблице.
    В [trip.ByID](internal/repository/pg/trip.go#L106) параметр `id` не используется:
    нет WHERE. После добавления двух тестовых рейсов запросы `/trips/1`, `/trips/2`
    и `/trips/99999` вернули `200` с первым рейсом.
    Исправление: WHERE по `trips.id`, явные aliases для вложенных DTO, корректная
    агрегация через `jsonb_build_object`/`jsonb_agg` либо отдельную загрузку остановок,
    сортировка по `stop_order`. Несуществующий рейс должен возвращать `404`.

11. **A11 / P1. Миграция ID автобуса ломается на старых данных.**
    [20251005230343_id_bus.sql](db/migrations/20251005230343_id_bus.sql#L19)
    преобразует прежний `trips.bus_id` (номерной знак) через `bus_id::integer`.
    Новые `bus.id` назначаются независимо. Подтверждено на минимальной старой схеме
    с FK и номером `A123BC`: миграция падает с invalid input syntax for integer.
    Даже числовой номер не гарантирует совпадения с новым ID.
    Исправление: перенос через JOIN `trips.bus_id = bus.license_plate` во временную
    колонку; затем проверка соответствий, ограничений и замена колонки.
    Подготовить путь обновления ещё не мигрировавших инсталляций и отдельные новые
    миграции для исправлений уже применённой схемы. Не переписывать историю миграций
    без учёта состояния установок. Проверить перенос и rollback на заполненной базе.

12. **A12 / P2. Частичное обновление автобуса записывает NULL в пропущенные поля.**
    [UpdateBus](internal/repository/pg/bus.go#L118) безусловно устанавливает все поля
    из указателей DTO. Подтверждено: обновление только `brand` существующего автобуса
    заканчивается `500`, поскольку остальные колонки NOT NULL получают nil.
    Исправление: добавлять SET только для переданных полей; валидировать значения,
    сохранять остальные поля и проверять наличие изменяемой записи.

13. **A13 / P2. Ответы теряют ID сущностей.**
    SELECT в [stop](internal/repository/pg/stop.go#L34),
    [driver](internal/repository/pg/driver.go#L33),
    [trip_stops](internal/repository/pg/trip_stops.go#L33) не выбирает ID.
    В моделях также встречается `json:"-,omitempty"`: это не эквивалент `json:"-"`,
    а имя поля `-` с опцией omitempty. Подтверждено: остановка с ID=1 возвращается
    без `id`, список водителей также не содержит идентификаторов.
    Исправление: явные DTO с `json:"id"` для ответов, `json:"-"` для действительно
    скрытых полей; ID из path, а не JSON, при обновлении. Проверить соответствие
    SELECT и DTO, включая отдельные ID рейса, автобуса и водителя.

14. **A14 / P2. Неправильная валидация и повторная запись ответа при ошибке.**
    [TripUpdate.Validate](model/trip.go#L57) не учитывает StartTime: обновление только
    start_time считается пустым. [Trip.Update](internal/handler/trip.go#L148)
    не возвращается после некоторых ошибок и дописывает второй JSON.
    Подтверждено: обновление start_time возвращает `500` с двумя склеенными JSON.
    Валидация категорий и статусов [сравнивает адреса полей с nil](model/bus.go#L54),
    что никогда не проверяет пустоту значений; аналогично DriverStatus.Validate.
    Исправление: валидировать значения и присутствие полей, добавить return после
    каждого завершённого ответа; проверить обязательные поля, допустимые статусы,
    положительные цены/вместимость/ID, координаты и временные интервалы.

15. **A15 / P2. Не различаются отсутствие записи, ошибка БД и неверный ввод.**
    Многие UPDATE не проверяют RowsAffected. Подтверждено: PUT
    `/api/v1/admin/stops/999999` возвращает `200 success` для отсутствующей записи.
    В user-сервисе ошибка БД превращается в UserNotFound, а Me сравнивает с другим
    типом ошибки. В ряде handler клиенту возвращается необработанный `err.Error()`;
    неверный ID часто даёт `500`. DriverStatus.All скрывает ошибки БД пустым списком.
    Исправление: единая классификация invalid input/not found/conflict/internal,
    проверка SQLSTATE и RowsAffected, корректные `400/401/403/404/409/500`, внутренние
    подробности только в логах. Зафиксировать политику идемпотентного DELETE.

16. **A16 / P1. Автоматическая привязка SSO-аккаунта по email без проверки доверия.**
    [findOrCreateUserFromSSO](internal/service/auth_sso.go#L80) привязывает новую
    identity к существующему пользователю по совпадению email. Google-модель читает
    `email_verified`, но [не передаёт его дальше](internal/sso/google.go#L49).
    Возможность захвата конкретного аккаунта не проверялась; подтверждён сам
    небезопасный критерий связывания. Также создание user и identity выполняется
    отдельными запросами без общей транзакции и обработки конкурирующих callback.
    Исправление: определить политику связывания: явное подтверждение владельцем
    локальной учётной записи либо строго определённые доверенные подтверждённые
    данные провайдера. Создание user+identity проводить транзакционно; корректно
    обрабатывать повторный вход и конфликт UNIQUE(provider, provider_id).

17. **A17 / P2. Ошибки userinfo провайдеров могут приниматься за данные пользователя.**
    [Google](internal/sso/google.go#L57) и [Yandex](internal/sso/yandex.go#L51)
    не проверяют HTTP status перед декодированием; обязательные ProviderID/email
    не проверяются. JSON с ошибкой может декодироваться в структуру с пустыми полями.
    Для исходящих запросов нет собственного конечного таймаута.
    Исправление: выделенный HTTP client с timeout, проверка статуса и ограничение
    тела ответа, валидация идентификатора и требуемых полей. Неполные данные
    не должны создавать пользователя или identity. Покрыть 401/429/500, timeout,
    некорректный JSON и отсутствие email мок-сервером провайдера.

18. **A18 / P2. Настройки HTTP и корректная остановка не подключены.**
    [server.New](internal/server/server.go#L18) фиксирует порт 8080 и не устанавливает
    таймауты, хотя конфиг их читает. DB_MAX_CONNS также заменяется константой 10.
    [main](cmd/server/main.go#L30) после сигнала просто завершается, не вызывая
    App.Stop; даже Stop не закрывает БД. Обычный ErrServerClosed обрабатывался бы
    как fatal. [RefreshMiddleware](internal/handler/middleware/refresh.go#L22)
    стоит после AuthMiddleware, поэтому не получает запрос с истёкшим access token,
    а его альтернативная ветка имеет несогласованные claims/cookie/TTL.
    Исправление: передать HTTP-конфиг в server, задать ReadHeaderTimeout и остальные
    таймауты; подключить MaxConns. При сигнале выполнить shutdown с deadline,
    остановить фоновые задачи, закрыть БД и логи; ErrServerClosed считать нормальным.
    Оставить один понятный механизм refresh: явный endpoint с обработкой 401
    на frontend либо согласованное middleware, без двойной проверки JWT.

**Порядок исправлений и критерии приёмки**

| Этап | Задачи | Проверка результата |
| --- | --- | --- |
| 1. Доступ и сессии | A01, A03, A04; тесты до исправления; единый пользователь в контексте; миграция хешей сессий | Роль user получает 403 на чужое управление; один refresh создаёт одну новую сессию; повторное использование отклоняется; logout отзывает её; logout/all отзывает все; из двух одновременных refresh проходит один; rollback не оставляет сессию |
| 2. Завершить SSO | A02, A05, A06, A09, A16, A17 | Callback без корректного state отклоняется до exchange; успех возвращает один 302; cookie работает на целевом домене; frontend получает access через refresh и загружает /users/me; входы Google/Yandex, отказ пользователя, timeout и повторный callback обработаны |
| 3. Конфигурация и CORS | A07, A08; синхронизация .env.example и Compose с новыми настройками | Пустой JWT_SECRET и неполные включённые провайдеры не запускаются; отключённые провайдеры недоступны; посторонние и похожие на localhost origin не разрешены |
| 4. Запросы, миграции и API | A10–A15 | Разные ID дают разные рейсы, отсутствующий ID даёт 404; остановки отсортированы; ответы содержат ID; частичные изменения сохраняют прочие поля; ошибки — один валидный JSON; обновление старой базы с номерами автобусов сохраняет связи |
| 5. Эксплуатация и CI | A18; регрессионные тесты предыдущих этапов в CI | HTTP_PORT/таймауты и MaxConns работают; SIGTERM завершает активный запрос в пределах deadline; scheduler и БД закрываются; CI выполняет go test, go vet и интеграционные проверки PostgreSQL/Redis |

Для финансовых полей отдельно согласовать единое представление: сейчас цена рейса
входом задаётся int, в ответах встречаются float32/float64, а в БД DECIMAL(10,2).
Необходимо выбрать целые минимальные денежные единицы либо decimal и явно
зафиксировать формат API. Также определить политику soft delete: колонка deleted_at

их нужно согласованно, с описанием новых переменных и поведения входа.
