# Собственный геостек: шаблон запуска и проверка

2026-11-01. Это opt-in шаблон в Git backend, а не изменение действующего
`corpord-infra`. Он не скачивает индекс/карту при обычном запуске. Существующий
backend без `PHOTON_BASE_URL` должен продолжать внутренний поиск остановок;
Photon не является источником рейсов, цен и свободных мест.

  [официальный release](https://github.com/komoot/photon/releases/tag/1.3.0).
  SHA взят из GitHub Releases API `assets[].digest`, проверяется сборкой.
- Eclipse Temurin `21.0.9_10-jre-alpine`, nginx `1.28.0-alpine`: версии и
  multi-platform registry digest закреплены в Dockerfile/Compose. Это
  воспроизводимая база пилота, а не обещание отсутствия уязвимостей: обновлять
  версии и digest отдельным PR с повтором smoke/импорта.

Публичные Nominatim, Photon demo и OSM tile servers не используются ни в адаптере,
ни в шаблоне. Нет автоматического fallback на сторонние серверы. URL Photon
настраивает оператор, пользователь не может выбрать upstream своим запросом.

## Локальная подготовка

Требуются Docker + Compose v2. Из этой директории:

```sh
docker compose build photon
```

Подготовить отдельные каталоги **вне репозитория** и собственные данные:

```sh
export PHOTON_DATA_DIR=/absolute/path/geo/releases/index-20261101
export MAP_DATA_DIR=/absolute/path/geo/maps
install -d -m 0750 "$PHOTON_DATA_DIR"
install -d -m 0755 "$MAP_DATA_DIR"
# Дать uid/gid 10001 запись в PHOTON_DATA_DIR, согласно политике хоста.
```

`PHOTON_DATA_DIR` — родитель `photon_data`, не сам `photon_data`.
Предварительно получить ограниченный региональный Photon JSONL export из своего
Nominatim/проверенного dump, сохранить URL, дату OSM, границы, SHA256, число объектов,
лицензию и совместимость схемы. Нельзя подавать `.osm.pbf` напрямую в Photon.
Имеющиеся официальные dumps могут быть гораздо больше нужного региона: сначала
проверить размер и заголовок. Преобразование/фильтрация потока JSONL должно
сохранять CountryInfo и ссылки addresslines; произвольный `grep` не годится.

Импорт **удаляет старый индекс** в выбранном каталоге. Импортировать только в
новый пустой release-каталог, никогда в активный volume:

```sh
docker compose run --rm --no-deps \
  -v /absolute/path/regional.jsonl:/import/regional.jsonl:ro \
  photon import -import-file /import/regional.jsonl -languages ru,en -country-codes ru
# Только после успешного импорта и проверки состава/давности данных:
docker compose up -d photon
```

Шаблон ограничивает Photon 2 GiB RAM / 2 CPU, JVM heap 1 GiB; nginx 128 MiB / 1 CPU.
Это безопасный старт для механической проверки маленького индекса, **не sizing
для всей России**. При OOM остановить и согласовать новый бюджет, не повторять
импорт бесконечно. Не менять sysctl хоста автоматически. Для регионального
пилота измерить максимальную память/RSS и длительность импорта, размер индекса,
временное дисковое пространство, старт до readiness, p50/p95 запросов и ошибки.
Обеспечить место одновременно под старый индекс, новый индекс, исходную выгрузку
и временные файлы, затем запас по фактическим измерениям. Исторический объём
planet/пример upstream не использовать как оценку нашего региона.

## Подложка и frontend

В `MAP_DATA_DIR` оператор размещает:

- versioned `.pmtiles` ограниченного региона;
- свои `style-light.json` и `style-dark.json`, согласованные со схемой слоёв архива;
- локальные glyph PBF (включая кириллицу) и sprites с совместимыми лицензиями;
- метаданные источников, даты, границы, SHA256 и `ATTRIBUTION.txt`.

Получать подложку можно собственной сборкой из OSM или региональным извлечением
из разрешённого PMTiles источника. До скачивания оценить объём/трафик и лицензию.
Готовой карты в репозитории нет. Нельзя просто направить стиль произвольной схемы
слоёв на другой архив и считать карту рабочей.

```sh
docker compose up -d tiles
```

Файлы карты должны читаться uid 101 (каталоги 0755, публичные assets 0644).
nginx отдаёт файлы на `127.0.0.1:8090`, поддерживает Range 206/416, ETag/If-Match,
HEAD и OPTIONS; gzip отключён, чтобы byte offsets относились к архиву.
CORS разрешён только для `http://localhost:3000`; перед публикацией заменить
точным origin frontend в `nginx.conf`. `Vary: Origin` сохраняется. Кэш 1 час;
архивы именовать по версии и не переписывать по прежнему URL. Сохранять старые
версии, пока браузеры могут использовать старый стиль. `pmtiles serve` CLI
создаёт ZXY endpoint, а не HTTP Range раздачу архива.
[Официальная инструкция PMTiles](https://docs.protomaps.com/pmtiles/cloud-storage).

Frontend получает `NUXT_PUBLIC_MAP_STYLE_URL` и
`NUXT_PUBLIC_MAP_DARK_STYLE_URL`. Все вложенные URL стиля (PMTiles, glyphs, sprites)
должны вести на свои HTTPS origins, доступные браузеру. Адреса контейнеров
`tiles:8080` браузеру недоступны. Публичное размещение требует отдельного TLS
reverse proxy и точных CORS/CSP правил. Шаблон ограничен loopback и сам ничего
в интернет не публикует. Нельзя включать карту до готовности валидного стиля и
данных. Проверить Network браузера на отсутствие внешних demo/assets endpoints.

Backend на том же хосте: `PHOTON_BASE_URL=http://127.0.0.1:2322`, `PHOTON_TIMEOUT=3s`;
в контейнере loopback принадлежит самому backend: подключить сервисы отдельным
reviewed Compose override в общую закрытую сеть и задать `http://photon:2322`.
API Photon не публиковать для браузера; backend предоставляет валидацию/лимиты.

## Готовность и адаптер

Photon `/status` проверяет состояние поискового сервиса; readiness дополнительно
должна проверять ожидаемый непустой запрос и допустимый возраст источника данных.
nginx `/healthz` подтверждает HTTP процесс, но **не наличие карты**: отдельно HEAD
архива, Range, стиль, glyph/sprite и визуальная проверка русских подписей.
Контролировать возраст данных, ошибки/429/timeout, длительность, RAM/disk и
объём запросов, не сохранять полный пользовательский адрес в access/application
логах. По умолчанию nginx логирует URL файлов карты; Photon доступен только внутри.

`internal/geo`: запрос 2–200 Unicode символов, limit 1–10, связанные lat/lon,
географические границы/NaN, язык ru/en, RU filter. Настраиваемый timeout не более
10 секунд, response body не более 1 MiB, redirects запрещены. Ошибки upstream не
передаются пользователю. Возвращаются только валидные Point с OSM N/W/R ID,
повторы убираются. ID `osm:N:123` — внешний геообъект, не продаваемая остановка.
Результат требует явного выбора обслуживаемой Corpord остановки.

## Проверки без реальной БД и публичных API

```sh
go test -race ./internal/geo
python3 deploy/geo/smoke_tiles.py
# Сборка из корня backend:
docker build -t corpord-photon:1.3.0 -f deploy/geo/Dockerfile.photon deploy/geo
python3 deploy/geo/smoke_photon.py
```

Smoke Photon действительно импортирует три вымышленных объекта типа **T** в
одноразовый индекс и выполняет запросы на русском, затем удаляет контейнер и
индекс. Зарезервированные OSM N/W/R не присваиваются вымышленным записям;
адаптер намеренно их не выдаёт. Это проверка импорт/serve и UTF-8, не проверка
реального покрытия РФ и не сравнение поисковой релевантности.
Tile smoke проверяет настоящую закреплённую nginx конфигурацию на 16 синтетических
байтах, включая Range, CORS/preflight, HEAD, ETag/cache; это не валидный PMTiles
архив и не доказательство отрисовки карты. Runtime/датасет пилот остаётся отдельным
приёмочным условием.

## Региональный пилот и обновления

До включения внешнего поиска/карты выполнить на реальных разрешённых данных:

1. Определить границы текущих направлений, не обещать Москву за пределами покрытия.
   Зафиксировать происхождение и дату, лицензии/атрибуцию, число объектов/размеры.
2. Заранее составить набор русских городов, полных/частичных адресов, автовокзалов,
   улиц с номерами, опечаток, одинаковых имён разных регионов и отсутствующих мест.
   Примеры запросов: Екатеринбург, Тюмень, «улица 8 Марта 145», Южный автовокзал.
   Их наличие в индексе и правильность результатов **ещё не подтверждены**.
3. Измерить import/startup/steady/peak RAM, диск/трафик и p95 на заданной нагрузке.
   Проверить lat/lon bias, пустой ответ, 429/timeout, независимость внутреннего поиска.
4. Проверить карту в обеих темах, кириллицу, attribution, offline внешнего геосервиса;
   записать конкретные версии/index snapshot и результаты в отчёт PR.

Для первого этапа обновление — полная сборка нового регионального индекса рядом
со старым. Остановить импорт, проверить `/status` и эталонные запросы на отдельном
временном порту, затем коротким перезапуском переключить `PHOTON_DATA_DIR`.
Проверить после переключения; при ошибке вернуть прежний каталог и образ.
Нельзя копировать активный embedded OpenSearch индекс обычным `cp`; сохранять
закрытый остановленный индекс либо поддерживаемый snapshot.

Согласовать период обновления по результатам пилота; до этого ручное обновление,
без cron с фиктивной гарантией свежести. Incremental update требует отдельного
Nominatim, `update-init` и упорядоченных обновлений с теми же фильтрами; JSONL import
сам по себе incremental не предоставляет. Не включать публичный update endpoint.
Для несовместимого schema upgrade пересоздавать индекс в новом release-каталоге.
Внутренние Corpord ID/связи при смене провайдера не меняются. Старую подложку
и glyph/sprite версии сохранять вместе со старым стилем для отката.
